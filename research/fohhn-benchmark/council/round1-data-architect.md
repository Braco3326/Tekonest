# Council round 1: data architect (Tomás Ferreira)

## Persona

Tomás Ferreira is a staff data architect with 16 years on versioned content, offline-first apps and simulation result stores.
His first question is: "If this Trial is reopened in two years, will it mean the same thing?" He is weak on UX and pedagogy.

## Findings

| # | Claim (file §) | Verdict | Why | Fix |
|---|---|---|---|---|
| 1 | "Deep-frozen" `inputs`, result "immutable once evaluated" (data-model §2, §4) | **Insufficient** | `Object.freeze` is lost on the JSON round-trip, so after a reload nothing is frozen. Also, `status: draft → evaluated` is itself a mutation of a stored record. | Use three layers: (1) a `DeepReadonly<Trial>` type; (2) a store API whose only writes are `append`, `rename`, `setNote` and `delete`; (3) on load, run a strict zod parse (not passthrough) and **recompute the fingerprint**, flagging a mismatch as corrupted. Do not persist drafts: the draft is the live state, and a Trial is written once, already in a terminal status (`frozen`, `evaluated` or `failed`). |
| 2 | `fingerprint = hash(inputs, refs)` (§2) | **Redesign** | It mixes two questions: "did the student edit?" and "did the content or engine change?". It also has no canonical form: Babylon floats like `-3.9999999`, `-0`, key order, the order of placements, and the a/b direction of connections. | Use `fp1:` + FNV-1a/cyrb53 (a sync hash) over canonical JSON. Sort keys. Sort arrays by `instanceId`, and normalise connections so a<b, then sort them. **Quantise at capture time**, not only in the hash: mm for positions, 0.1° for angles, 0.01 dB, 0.01 ms. Map `-0` to `0`. Exclude `name`, `note`, `createdAt` and `view`. Compare refs separately, so they drive a separate banner. |
| 3 | `EvalSettings.band/weighting` inside `inputs` (§2) vs "band switch is UI only" (crosswalk row 6) | **Contradiction** | If the band is in the fingerprint, switching bands makes the result stale. | Split the settings in two. `ComputeSettings` (fidelity, temperature, air, drive) goes in the fingerprint. `DisplaySettings` (band, weighting, quantity) does not, and the results are stored per computed band. |
| 4 | `roomRev` = "hash of the room file used" (§2, §3; crosswalk row 17) | **Underspecified** | Which file is hashed: the KB file, `content/rooms` or `rooms-acoustics`? A lighting edit would mark every trial "salle modifiée", and over-invalidating trains students to ignore the badge. | Have `sync-rooms` compute `geometryRev` (dims, zones, openings) and `acousticsRev` (RT60, volume, listener data) as content hashes written into the emitted files. Hash only what the evaluation consumes. |
| 5 | `speakerAcousticsRevs`, `engineVersion: "eval-b@0.1.0"`, `catalogVersion: 1` (§2) | **Weak** | Revisions bumped by hand get forgotten. `catalogVersion` has been `1` forever, so it is not a revision. | Make revisions **content hashes generated by tools**. Guard `engineVersion` with golden evaluation fixtures: if the outputs change and the version did not, CI fails. Replace `catalogVersion` with a hash of the catalog entries of the devices used. |
| 6 | Room geometry, zones and speaker data by ID + rev only (§3) | **Partly reject** | A by-ID reference plus a rev can *detect* drift but cannot *show* what the student saw. Fohhn's geometry-outside-snapshot design is a weakness, not a model to copy. | Denormalise what the evaluation consumes (about 1–2 KB): the resolved zone rectangles, the room dimensions and volume, the `SpeakerAcoustics` numbers used, and device labels. The rev then labels the data; it does not replace it. |
| 7 | Trial embeds `Pick<SavedRig,…>` (§2) | **Agree: embed** | A `SavedRig` is keyed by a name that is silently overwritten (`shelf.ts:164`), so a reference to it would rot. | Embed it. Allow `fromRigName?` as provenance metadata only. |
| 8 | SavedRig v2 + v1→v2 migration (§4, §6) | **Agree, with a hazard** | v1 files exist both with and without `positions`. The bigger risk is the reverse direction: an old tab or cached build runs `saveRig` on a v2 file, gets a version mismatch, **writes a fresh v1 file and wipes the v2 rigs** (`shelf.ts:154-166`). | Use a new key, `audio-sim/rigs.v2`, and migrate by copying while v1 stays read-only. Set `roomId: null` for migrated rigs (never guess it). Make v2 = `{name, savedAt, design: DesignState}` so there is one codec. Unit tests cover v1 without positions, v1 with positions, malformed positions, and v2. |
| 9 | Trials: "version mismatch resets with notice" (§4 Persistence) | **Block** | The `ProgressStore` pattern deletes data (`removeItem`). Trials are student evidence, not conveniences. | For an unknown, future or corrupt payload, **quarantine** it to `audio-sim/trials.quarantine`, open read-only and offer an export. Never call `removeItem`. |
| 10 | Cap of 50 trials per room (§4); grid storage (§2 `TrialResult.grid`) | **Quota breach** | Inputs are about 3 KB per trial, so 50 × 32 = 1,600 trials ≈ **4.8 MB with no grid**. That is the whole per-origin localStorage budget (about 5 M chars), and the origin is shared with `progress`. A grid for a 18 × 20 m zone at 1 m is 399 cells. That is about 2.4 KB at 1 decimal and about 7 KB at full float precision, and ×9 bands gives up to about 65 KB per trial. In the worst case that is **about 100 MB**. When the quota fills, `ProgressStore.save` degrades **silently** to memory, so learning history is lost. | Use a **global** budget: about 150 trials and about 1.5 MB measured before each write, with a hard failure the student sees. Store points and the summary by value. Store grids as int16 at 0.1 dB in base64 (about 1.1 KB per band), or keep them only as an evictable cache plus a `gridHash`, recomputing and verifying them when the refs match. Move to IndexedDB only through an ADR. |
| 11 | Naming: `Trial` / "Essai" (§0) | **Agree** | It avoids the `RigSnapshot` collision. | Ban "snapshot" in new identifiers, enforced by a lint grep. Keep the `DesignState` and `Trial` names, and never call a `DesignState` a rig. |
| 12 | `Provenance` union (§2) | **Extend** | Numbers parsed from KB `key_specs` strings have no `kb` kind, and the array cannot say which field came from which source. | Add `{kind:'kb', kbId, kbRev, quoted, parser: 'v1'}`. Use `provenance: Partial<Record<field, Provenance>>`. A zod refine requires every non-null numeric field to have a provenance entry. |
| 13 | `LessonObjective` outside `^R[1-8]$` (§6) | **Agree** | It avoids reopening the closed enum, and the coach/onboarding regexes stay valid. | Give objectives an `O-` id namespace. Never log an objective miss as a `MistakeRecord.ruleId`. When a score is shown, freeze `{target, tolerance}` into the Trial alongside it, because levels change. |
| 14 | JSON export "schema-versioned" (§4) | **Specify** | An export that holds only ids is meaningless off-device. | Export `{format:'tekpractice.trial', formatVersion:1, app:{version, commit}, trial, embedded:{room, speakers, devices}}`. On import, re-hash, issue a new id and keep `importedFrom`. |
| 15 | Separate `content/acoustics/speakers.json` (§6) | **Agree** | The catalog is the hand-kept source of truth scoped to A1–D1, while acoustics covers proposal ids too. | Use a file `version` plus a per-record content-hash `rev`. A validator checks that each `deviceId` exists in the catalog or the proposals and that each `deviceId` appears once. |
| 16 | `sync-rooms` emits a second file (§6) | **Agree** | `RoomFile` is non-passthrough, so this is additive with no effect on the runtime schema. | Write the revs into `index.json`. Add a test that two runs produce byte-identical output, and one that the rev changes only when consumed fields change. |
| 17 | Tests (prototype-brief §4, phase 1 exit) | **Too thin** | "Freeze immutability" tested on in-memory objects proves nothing after a reload. | Write: property tests of fingerprint invariance and sensitivity; golden fingerprint strings; tamper-on-load detection; quota simulation with a 5 MB fake storage; a two-version clobber test; an export → import round-trip; golden evaluation fixtures per `engineVersion`. |

## Position

I support **B now**: Essais without acoustics.

I support **C only as a later gate**, capped at fidelity (b). Its schema hooks are reserved now (`refs` fields nullable, `ComputeSettings` defined), but no acoustics data ships before these conditions are met:
- findings 2, 4, 5, 9 and 10 are implemented and tested in phase 1;
- the embedded-data rule (finding 6) is accepted in ADR-0011.

Phase 1 is the cheapest place to get immutability, fingerprints, migration and quota right. If those are wrong, C would build trusted-looking numbers on mutable, unbounded storage.

**A** is not needed. B also fixes the untested `SavedRig` persistence, which is a real defect today.

## Non-negotiables

1. No silent mutation. A Trial is written once; only its name and note can change, and the fingerprint is re-verified on every load.
2. No silent deletion. Unknown or corrupt payloads are quarantined, never reset, and every write failure is surfaced to the student.
3. A global storage budget is measured in bytes, and the Trials store can never starve `audio-sim/progress`.
4. Every stored record carries a schema version, and the fingerprint algorithm is versioned (`fp1:`).
5. Content revisions are tool-generated hashes, and `engineVersion` is guarded by golden fixtures.
6. The inputs the evaluation consumed are embedded by value: geometry, zones and speaker numbers.
7. SavedRig v2 uses a new key, and a test proves that old builds cannot clobber it.

POSITION: B (Essais without acoustics; C-ready schema, C gated on phase-1 invariants) | CONFIDENCE: 80% | RISK: I would block reset-on-mismatch for trials, the per-room-only cap and grids in localStorage, hand-bumped revs, and a SavedRig v2 that reuses the v1 key.
